# Candidate classification schema v3 — intrinsic profiles + signed interaction graph

**Date:** 2026-09-09  
**Status:** research classification schema; maintained source and `main` unchanged.

## Governing correction

Candidate properties and candidate-to-candidate effects are different kinds of information.

The previous schema still left several relational ideas on individual candidate rows (`amplification potential`, `exclusion risk`, `coverage displacement`). Those are now removed from intrinsic candidate classification.

The model is split into two independent structures:

1. **candidate profile** — properties of one candidate considered on its own;
2. **directed signed interaction graph** — what adopting candidate A does to candidate B.

Neither structure is reduced to one score.

## A. Intrinsic candidate profile axes

Every candidate, including all current core candidates, receives the same intrinsic profile.

1. **Projected effectiveness vector** — projected nodes/proof work, time-to-proof, NPS/per-node cost, memory footprint, TT traffic, depth/progress, parallel efficiency, etc.; mechanism + confidence + regime recorded separately.
2. **Measured effectiveness vector** — only actually measured metrics, preserving adverse and positive results separately.
3. **Expected usefulness / adoption likelihood** — probability the underlying idea appears in the eventual solver in some form.
4. **Proof-authority class** — semantic foundation, exact reduction, exact proof, admissible bound, ordering hint, scheduler/resource hint, cache representation, etc.
5. **Benefit mechanism(s)** — direct mechanisms by which the candidate itself changes work/resources.
6. **Hot-path performance risk**.
7. **State/resource footprint cost**.
8. **Precomputation / cold-path cost**.
9. **Incrementalizability**.
10. **Amortization horizon**.
11. **Cache/locality effect**.
12. **Parallelism interaction as an intrinsic execution property** — e.g. branch divergence or synchronization demand generated by the candidate itself; pair-specific parallel effects live in the graph.
13. **GPU suitability**.
14. **Reroot/persistence value**.
15. **Generality/domain scope**.
16. **Correctness-risk severity**.
17. **Validation difficulty**.
18. **Architectural lock-in / reversibility**.
19. **Evidence maturity**.
20. **Implementation-form risk**.
21. **Benefit consistency / variance**.
22. **Regime sensitivity**.
23. **Information half-life**.
24. **Stage locality**.
25. **Multi-problem leverage / direct optimization encapsulation** — the distinct problems the candidate itself solves through one mechanism.
26. **Enabling/substrate leverage** — distinct from direct encapsulation: how broadly the candidate provides reusable state/precomputation for other optimizations.
27. **Substrate role** — producer, consumer/free-rider, dedicated substrate, replacement, or co-owner-risk.

### Removed from intrinsic rows

The following are **not intrinsic candidate properties** and are no longer stored as such:

- amplification potential;
- exclusion risk;
- coverage displacement;
- synergy-with-core;
- substitution pressure;
- marginal saturation caused by another candidate.

Those are all relational effects and belong in the signed interaction graph.

## B. Directed signed all-candidate interaction graph

For every ordered candidate pair `(A,B)`:

```text
I[A -> B]
```

records the effect of adopting A on B's usefulness, cost, applicability or viability.

Scale:

- `+4` transformative amplification
- `+3` strong synergy
- `+2` clear positive synergy
- `+1` mild positive interaction
- `0` explicitly assessed neutral/additive
- `-1` mild exclusion pressure / saturation
- `-2` material displacement/interference
- `-3` likely exclusion/substitution
- `-4` fundamental exclusion/incompatible contracts
- `null` unassessed

The scale is ordinal and must not be summed without a separately defined decision model.

Each edge separately records:

- projected value;
- observed value when crossed evidence exists;
- mechanism;
- relation kind;
- confidence;
- regime;
- evidence basis.

### Relation-kind examples

Positive:

- cost-sharing
- state-simplification
- applicability-increase
- proof-order
- cache-retention
- shared-metadata
- validity-enabling
- parallel-duplication-reduction

Negative:

- saturation
- overlap
- subsumption
- substitution
- resource-interference
- cache-interference
- state-identity-conflict
- support-semantics-conflict
- proof-authority-conflict
- hot-path-cost-conflict
- architectural-lock-in

## C. Compatibility and dependency remain categorical relations, not signed-effect values

The signed graph answers `does A help or push out B?`.

It does **not** answer every relational question. Keep these separately:

### Pairwise compatibility / relationship type

Examples:

- complementary
- co-design-compatible
- overlapping but compatible
- alternative realization
- conditionally incompatible
- fundamentally incompatible

A candidate can be compatible with another yet strongly displace it (`-3 subsumption`).

### Dependency / prerequisite relation

Record explicit prerequisites independently. A strongly positive edge often but not always implies dependency.

Example:

- `RID -> AUTO = +3` can coexist with `AUTO depends_on RWS/RID-style residual identity`.

## D. Saturation is represented directionally

What was previously called `marginal-value saturation` is now an edge mechanism.

Example:

```text
FMAC -> IMPL = -1 saturation
```

means FMAC removes some states that IMPL would otherwise prune. This can coexist with a positive mechanism on the same pair:

```text
FMAC -> IMPL = +1 cost reduction because IMPL is queried only at decisions
```

If both mechanisms are material, store them as separate regime/mechanism observations rather than forcing one averaged sign. A final interaction value may be recorded only for a named regime after reasoning about net effect.

## E. Direct multi-problem leverage vs enabling leverage

This distinction is mandatory.

### Direct encapsulation

A problem counts when the candidate itself performs the optimization.

Example: FMAC directly solves:

- deterministic transit-state removal;
- TT traffic reduction for those states;
- recursion/decision-node reduction.

### Enabling leverage

A substrate can make many other candidates cheap without itself doing their work.

Example: RID enables:

- AUTO transform maps;
- implication closures;
- Allis solves masks;
- cardinality metadata.

RID does not get credited as directly performing all those optimizations.

This prevents unifying substrates from receiving artificially inflated direct-optimization counts while still recording their strategic importance.

## F. Evidence discipline

Every intrinsic assessment uses:

```text
value/magnitude
mechanism
confidence
regime
evidence basis
```

Every graph edge uses the same structure and additionally distinguishes:

```text
projected interaction
observed interaction
```

Negative implementation evidence updates the narrowest justified candidate form. It does not automatically create negative edges against the broader underlying idea.

## G. Core is derived, not structural

`core` remains a derived label based primarily on adoption likelihood and architecture reasoning.

Core candidates:

- receive the same intrinsic axes as every other candidate;
- participate as ordinary source and target nodes in the signed graph;
- can negatively exclude one another's implementation forms;
- can be displaced by stronger later candidates.

There is no special `core synergy` table in the authoritative model; core slices are merely views of the all-candidate graph.
