# C4-0009-C3 — Compact CUDA-BSFP work diagnostic v0

**Status:** Working experimental diagnostic profile under C4-0008/C4-0009 and Q1.

## Purpose

C3 diagnoses the measured 6x5 CUDA-BSFP scaling wall without pretending a partial execution is a solved game. It executes a fixed, predeclared prefix of the same C1 device-owned recurrence and reads observer counters only after that prefix has completed.

The first profile is frozen to:

- geometry: 6x5 connect-4;
- ownership frontier capacity: 8,192 records;
- candidate tile capacity: 2,048 records;
- shard capacity: 64 supports;
- block size: 128 threads;
- static prepared-DAG epoch limit: 1.

No CPU oracle is admitted for this large diagnostic profile.

## Semantic boundary

The device recurrence is unchanged. Host code chooses the static epoch prefix before ignition and cannot inspect a counter to decide which BSFP transition executes next. The plan remains one-shot: a prefix diagnostic cannot later resume from host-observed state and call that continuation one semantic solve.

C3 therefore permits:

- device-owned cofactor, terminal, pair, normalization and rank work identical to C1;
- observer counters written alongside that work;
- readback only after the selected static prefix completes;
- rank/support workload summaries derived on the host after execution.

C3 does **not** permit:

- root W/D/L claims;
- `closure: full-root`;
- recursive search or host semantic progression;
- silent frontier/candidate truncation;
- adaptive epoch selection from observed intermediate counters.

## Counters

Per support, the diagnostic records exact u64 totals for:

1. generated Cartesian pair candidates;
2. retained-frontier subset checks;
3. iterations of the same-cardinality `prior < i` duplicate scan;
4. exact duplicate hits;
5. records presented to normalization, including carried retained records;
6. normalization calls;
7. pair candidates generated by terminal subtraction;
8. pair candidates generated by aggregate move intersection;
9. cofactor normalization input records;
10. terminal-intersection normalization input records;
11. terminal-union normalization input records;
12. aggregate normalization input records.

The host may derive the existing 43-phase candidate-visit count as `43 * normalizationInputRecords`. These diagnostics do not become correctness authority.

## Evidence meaning

A successful C3 Q1 case means only:

- the exact pinned dependency pair opened and executed the selected device prefix;
- the prefix completed without capacity/runtime failure;
- diagnostic counters were read successfully;
- the result was labeled as a partial-rank diagnostic and not a root solve;
- cleanup was graceful.

C3 does not establish a 6x5 W/D/L result, complete rank closure, performance superiority, or a 7x6 solve.

## Current question

Use the first epoch to distinguish among the leading measured hypotheses:

- genuine frontier/candidate growth;
- quadratic duplicate-scan work;
- terminal-subtraction pair explosion;
- 43-pass normalization overhead;
- concentration in a few pathological supports.

The next optimization must be selected from the observed cause rather than from primitive throughput alone.
