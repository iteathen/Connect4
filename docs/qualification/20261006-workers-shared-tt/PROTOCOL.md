# Worker count / shared TT capacity experiment

Owner-approved matrix: workers 2,3,4,5,6; shared TT 1,2,4 GiB. Private TT stays 256 MiB per worker. Empty 7x6 root solve, no RLC, book, oracle, persisted cache or fixed opening. Optimized native32 layout stays unchanged. Production defaults are not modified.

Runtime/package snapshot: Connect4 `7ae122723128ddb65b1d5fa3293410bb3e54e14d`, IsoMax rc.3, frozen producer `e6580e951c8318395446dd5916482efddc3d33fd`. Runtime v27.0.0-nightly20260928b59840b593, V8 14.6.202.34-node.36, i5-12600K, retained 2400/9600 inlining flags and startup bridge. No legacy affinity preload, process mask assignment or memory/JIT environment overrides. Public discovery selects the first N distinct P-core targets and verifies every binding before READY. Center/live worker policies retain their existing assignment; changing worker count also changes the aggregate private memory and policy mix.

Each fresh process uses the exact `run.mjs` child launch flags with only `--workers N --shared-entries E`; E is GiB*33554432. No other setting changes. Primary time: all-ready through actual empty-root construction and exact result. Startup, cleanup, external wall, total process CPU and OS peak RSS recorded separately. Hot counters and process cycles remain unavailable. Default search timeout 600s and initialization timeout 120s; external cleanup ceiling 750s. Failures/timeouts are retained, never treated as solved samples.

Stage 1: one trial of all 15 cells, in a frozen interleaved order to avoid measuring all small or all large capacities together. This does not fully control temperature, SMT-sibling interference, OS/background work or physical-core differences.

Stage 2: for each worker count, repeat its fastest EXACT screening capacity twice, ties choosing smaller capacity. If six-worker 4GiB is not that winner, repeat it twice as a contemporary default control. Comparisons without repeated alternatives remain exploratory; screening winners may regress toward the mean. If a repeat contradicts the winner ranking materially, report ambiguity and gather relevant extra paired trials before selecting a rule.

Confirmation refinement after the complete screening, frozen before repeats: also repeat alternatives within 5% of the fastest screening sample twice. This selects four-worker 2GiB (59.127s versus 58.188s), alongside every worker count's 4GiB winner. Five percent is a repetition-selection rule, not a retention threshold or evidence of statistical equivalence.

Always inspect native32 entry bytes, exact WDL/move, worker counts, actual bindings and clean exit after each trial. Expected-answer comparison is only after the timed process has returned. If source identity, affinity, layout or cleanup fails, stop the campaign; do not change code to rescue it. Before each run record available physical memory and refuse allocation when estimated TT+2GiB support/runtime margin exceeds free RAM. This is a run admission guard, not a proposed product sizing rule.

Each completed trial is committed promptly; refs are pushed at phase boundaries and every three screening trials. Raw outputs, invocation, machine snapshots, measurement and validated summary live under the case directory. `matrix.ps1` is a resumable external measurement driver, not solver/runtime code. `-ValidateOnly` checks the frozen plan without running a solve.

Analysis: tabulate solve time against worker count and capacity; consider memory-efficient near-ties and whether optimal tested capacity rises, stays constant or saturates. Compare a constant capacity rule with per-worker scaling rounded to supported power-of-two capacities. Do not force a linear relationship or extrapolate beyond six workers from this host. A proposed initialization rule must separately budget available RAM, private TTs, support plans and runtime, and respect geometry/layout limits. Measurements here cannot establish performance on other processors, operating systems or dimensions. No automatic sizing code is authorized by this measurement protocol.
