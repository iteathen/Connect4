## DP-01 — Cross-boundary relational structure

PASS with findings.

The strongest cross-boundary mismatch is not “parallelism” in the abstract:

```text
semantic object:
    ranked canonical q_r dependency DAG

execution visibility:
    manager-visible q_r nodes
    + long private worker dependency subtrees
```

A q dependency is globally deduplicable only after it crosses back into manager-visible structure. While it remains private, sibling workers can independently materialize the same q. This gives a common cause for #78 and much of #89-#95: **semantic q visibility delay**.

Second exact finding: native frontier classification establishes a stronger precondition for the following mover transition than the residual kernel currently consumes. If `nativeFrontierCode(state)` is unresolved or forced rather than exact, own-win precedence proves there is no playable mover singleton. For every legal landing cell admitted after that classification, the mover cofactor cannot produce `RESIDUAL_TERMINAL_WIN`.

## DP-02 — Constraint-structure discovery

PASS with one new exact closure candidate.

Current precedence:

```text
native frontier:
    terminal
    bilateral exhaustion
    playable mover singleton -> exact immediate win
    multiple opponent singletons -> exact loss
    single opponent singleton -> forced move
    otherwise quiet
```

Therefore, after exact cases are excluded:

```text
(no playable own singleton)
+ legal landing cell
    ->
ownTransition(ownClass, landingCell) is nonterminal
```

This is a semantic precondition, not a trust/validation assumption. It can potentially remove both:
- the singleton terminal fast-path check in a worker-specialized mover cofactor;
- the per-active-term `target === terminal` branch, because terminal reduction can arise only from consuming a singleton term.

Public/general `ownTransition` remains unchanged unless separately justified.

## DP-03 — Interface / port correspondence

PASS; existing ownership mostly correct.

Manager -> worker currently transports legal move history, not pool-local IDs. This is correct because pool-local residual IDs are not portable semantic identity.

The executor also performs:
```text
fresh IsoMax message
    -> structuredClone(message)
    -> spread into another object
    -> Worker.postMessage clone/transport
```

For the current IsoMax caller, the explicit pre-dispatch clone may be redundant because the submitted message is freshly constructed and not mutated after submission. However, the executor is shared/generic and #85 showed manager-side object churn is measurable but not dominant. This route is recorded as a low-priority representation-excess lead, not a new issue.
